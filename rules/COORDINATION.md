## 二、状态机

```
需求侧:  登记 ──▶ 分析中 ──▶ 已定稿
                              │
任务侧:                        ▼
          已定稿 ──▶ 已认领 ──▶ 开发中 ──▶ 已交付 ──▶ 已验证 ──▶ 已验收（终态·冻结）
                        ▲                    │
                        └──── 返工 ◀─────────┘

任意非终态 ──▶ 阻塞 ──▶ 回退到进入前的状态
```

**「已验证」独立成态**，是为了让「形式有效是实质验收的前置」**由结构保证**：

```
已交付 ──verify──▶ 已验证 ──accept──▶ 已验收
```

`accept` **只可能来自已验证**。于是「未校验即验收」在结构上不可达。

| 动作 | 判什么 | 谁发 |
|---|---|---|
| `verify` | **形式**：证据齐否、路径存在否、门禁退出码为 0 否 | TL 或 commander |
| `accept` | **实质**：逐条比对验收标准 | PM |

**需求与任务共用同一个编号。** 需求在**定稿那一刻**升级为任务，编号不变。
好处：结构上不可能出现「需求翻牌了但任务不见了」。

## 四、不变量（协调器强制，不是靠自觉）

**一·编号唯一。** 发号与登录取号在**同一次持锁事务**内完成，撞号在结构上不可能。

**二·一条目一认领人。** 后来者被**拒绝**，不是"自行避让"。

**三·状态单向。** `✅` 不可倒回；未终态的转换不得跳过中间态。
「未校验即验收」「未定稿即交付」在结构上不可达。

**四·分权。** 每个动词有允许的角色集；越权**拒绝**。

**五·界内。** 实际改动必须落在条目白名单内——**交付时与合并时各判一次**。

**六·乐观并发。** 请求须带**期望版本号**；不符即拒并返回当前快照。
**这是治「陈旧视图」的那一条**——旧机制下两个会话可以先后读到同一状态再各自写，
于是产生了一批「竞态／重试」提交；版本号让过期的一方**必然失败**。

**七·就绪判定。** 认领开发前，协调器算：

```
就绪(dev, 线) =
      状态 == 已定稿
    ∧ 前置全部终态
    ∧ 认领人为空
    ∧ 白名单 ∩ 所有在办条目的白名单 == ∅     ← 从纪律变成函数
    ∧ 该线在办数 < 线内预算
    ∧ 优先级已定
```

**「白名单互不重叠」不再靠自觉**——它由协调器算出。TL 派单前只查可认领清单。

**八·审计读真实文件。** 审计工具读**磁盘上的视图**，不读协调器的内存或缓存——
否则就成了「自己证明自己」。

## 五、四要素

**无白名单不成条目。** 定稿必须四要素齐，**缺一即拒、状态不变**。

另可声明**条目级约束**（`--constraint`，可重复）——把"本条的硬要求"变成**可核的声明**：

| 约束 | 判据 | 撞上了怎么办 |
|---|---|---|
| `zero_migration` | 改动不得触及迁移目录（提交闸核） | 确需迁移 ⇒ **另立条目**（dba 评审 ＋ ops 窗口） |
| `no_doc_change` | 本批不改文档 | 要改 ⇒ 与面同批，或另立条目 |

**没有判据的约束当场拒**（`validators.KNOWN_CONSTRAINTS` 未登记的）：声明了却没人能核，
等于一句安慰——缺口必须暴露。

| 要素 | 要求 |
|---|---|
| **修改范围白名单** | 非空 |
| **不动清单** | 显式声明；空列表合法（＝明确声明"无"） |
| **前置** | 允许为空（＝无前置）；引用必须存在，且**不得成环** |
| **验收标准** | 非空，且**结构化**（见下） |

**验收标准必须结构化**——这是本体系最值钱的一处：
它让「回标必须带实证」从一条纪律变成**可校验条件**。

```
acceptance:
  - type: test       cmd: "<门禁命令>"             expect_exit: 0
  - type: negative   desc: "未注入仍 200 ⇒ 必红"
  - type: evidence   path: "worktrees/T-D-194.SUBMISSION.md"
```

| 类型 | 判据 |
|---|---|
| `test` | 命令退出码 = 期望值 |
| `negative` | 描述必须有——**无负例的验收不算验收** |
| `evidence` | **路径存在且可读** |
| `manual` | 只记描述；**不可交给机械校验** |

**功能条目的验收必须含闭环路径**（2026-10-01 用户定）：
至少一条「**入口动作 → 系统可观测反应**」的端到端断言；**只交模块单测 ＝ 未闭环**，
回标时标出缺口并注明补测去向——「单元都绿」不等于「这条路走得通」。

**认领即冻结**：范围／验收／口径以**认领那一刻的快照**为准，此后改动**一律走新条目**。

### 五·五 无条目不做工（调研与探针同等对待）

**调研亦须条目化**（2026-10-01 用户定）：**spike／探针／验证性脚本与功能开发同等对待**——
先登记、立项（可标「调研型」）后方可动手，**无条目不做工**。

探针提交必须**同批**把发现落回条目（含发现／根因／候选方案；未定论者标「待对账」）。
**发现只进归档面而未落条目 ＝ 交付未完成**，不得充当后续设计的前提或依据。

> 为什么要单列：探针最容易被当成"顺手跑一下"——它没有白名单、没有验收、没有条目，
> 于是它产出的结论**没有任何可追溯的落点**，却会被当成设计依据。
> 「同等对待」不是加重流程，是让结论有主。

## 六、编号

| 项 | 规则 |
|---|---|
| 形态 | `类型-线码-N`，**线内独立计数**（`T-D-194`／`R-ACL-67`／`OPS-162`） |
| 发放 | **一律经协调器**，原子发放——**禁手工自选号** |
| 迁移件 | revision 以主干**迁移目录**（见绑定 §迁移）当前最大号为基准自增 |
| **串行族** | **同时只允许一个在飞占号**（`pending`），落物或让号后才放下一个 |

### 六·五 需求必须由用户确认（commander 的专门前置）

**commander 是用户接口，同时又是需求的形式化者**——这两个身份重叠，
所以「用户要的」与「它认为用户要的」必须是**两条独立留痕**，否则事后分不开。

| 步 | 谁 | 动词 | 说明 |
|---|---|---|---|
| 1 | 用户 → 会话 | — | 用户明确说要什么 |
| 2 | 会话 | `coord confirm` | 记下**用户原话**，绑定**内容指纹**（线别＋标题），12 小时过期 |
| 3 | commander | `coord register --origin commander` | 发号时**消费**那条确认；没有 ⇒ `E_NO_USER_CONFIRM` |

判据（可核，不是散文）：**内容指纹相符 ∧ 未消费 ∧ 未过期 ∧ 带用户原话**。
确认**一次性、内容绑定、会过期**——"确认了 A 拿去发 B"、"确认一次发十条"、
"上个月的'是'发今天的需求"三种形态都被结构挡住。
留痕落在条目上（`confirmed_by`／`user_said`，`coord trace` 可读），
存量缺口由 `coord audit` 报 `E_NO_USER_CONFIRM`。

**只管 commander 来源的需求**：开发中发现（`line`）／DBA／OPS／PM 来源照旧登记；
`raise`（TL 评估后登记）走它自己那套规则。**已知残留（与 `--role` 同级）**：
记录人自报无鉴权——协调器把它连同原话记进事件流，伪造的话，用户读到原话一眼就知道。

**为什么迁移件要串行**：它的**号顺序就是链位顺序**。
两个件同时占号、各自把父节点接到当时的 head 上，合起来必然**分叉成两个 head**——
升级目标不唯一。所以迁移的收口有三处，**放号是第一处**：

| 收口点 | 谁执行 |
|---|---|
| 放号 | 协调器（串行族闸，`E_NUMBER_INFLIGHT`） |
| 提交 | `tools/commit_gate.py`（含迁移链腿与保真腿） |
| 合并 | `merge.py` 链位闸（判据与提交闸**同源**） |

判据只有一处实现：`coordinator/bg_coordinator/migrations.py`。
**已落库件禁止就地改写／删除**（判据 `[6]`）挂在**提交与合并**两处，跟着同源判据一起生效——
它跟链位分叉是同一类事故：**合入才爆**（改的是已执行过的历史，改不动已建的表）。

**由此消失的一整类问题**：号段空洞、真脱同步、待回填——
它们全是**并发写簿记**的产物，簿记被原子发号取代后不再存在。

## 九、上下文纪律

**上下文是稀缺资源，与子代理额度同级。** 本节把「怎么读」定死。

**规模有预算、有闸**：冷启动（`AGENT.md` ＋ `agents/<角色>.md`）与按需面（`rules/*.md`）
的总量都在 `bg_coordinator/context.py` 定了上限，`tools/context_budget.py` 现算并拦截——
**超了不是警告，是红**。要加内容先删，或显式抬预算（改一处常量 ＋ 写明理由）。

**教训与实测（为什么这么定）见 `rules/COORDINATION-details.md` §九**——判据在下面四条，数据在分册。

### 9.2 四条规则

**其一·读命令必须有界。** 任何读命令的默认输出必须有**条数上限**与**字段宽度上限**。
超限即折叠，并显式告知「另有 N 条」。要看全部，必须显式请求。
**默认给结论，全量是例外。**

**其二·明细按需取，不做批量预读。** 谁需要详情，谁发起一次有界查询；
**不把明细预加载进任何人的起始上下文**。

**其三·投影只渲染载荷字段。** 任务视图渲染的是**载荷**（编号、状态、认领人、白名单、验收条数），
**不是案卷**。证据与经过住在事件记录里，从投影里出去。

**其四·一条长文案不许独占上下文。** 任何字段显示超过宽度上限即裁剪。
