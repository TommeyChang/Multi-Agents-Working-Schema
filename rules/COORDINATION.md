# COORDINATION.md — 任务协调

> 任务怎么流转、状态怎么变、编号怎么发、记录长什么样。
> 本文件是这四件事的**唯一权威**。

---

## 一、两类东西：活状态与记录

**活状态**回答「现在是什么」。它住在**协调器**里，**不在仓库内**。

**记录**回答「曾经发生过什么」。它住在**事件日志**里，**只追加、永不改写**。

| 东西 | 位置 | 谁写 | 能否重建 |
|---|---|---|---|
| 事件日志 | 仓库之外，`events.jsonl` | 协调器追加 | **不可重建** |
| 状态缓存 | 仓库之外，`state.json` | 协调器 | 可（从事件重放） |
| 视图 | 仓库内：任务视图 ＋ 人读报告 | 协调器渲染 | 可（从状态渲染） |

**三条推论**：

**其一·状态变化不产生提交。** 状态住在仓库之外，改状态不碰 git。
历史版本要求「改共享文件 ＋ 同提交入库」，于是每次状态变化都在主干上制造一个合并面。

**其二·视图不参与分支合并。** 视图是渲染产物，**不是被各会话编辑的版本化文件**。
因此它**不可能成为合并冲突面**。

**其三·视图内容未变则不写、不提交。** 刷新不产生提交面。
这条是有意设的：只要渲染里出现一个会漂移的字段（时间戳、日期列），
每次刷新就会变成一次新提交——**无意义的刷新不得变成合并面**。

**事件日志只准追加。** 就地编辑 = 状态被静默污染，且**不可重建**。
这是全体系里唯一一处「错了无法挽回」的地方。

## 二、状态机

```
需求侧:  登记 ──▶ 分析中 ──▶ 已定稿
                              │
任务侧:                        ▼
          已定稿 ──▶ 已认领 ──▶ 开发中 ──▶ 已交付 ──▶ 已验证 ──▶ 已验收（终态·冻结）
                        ▲                    │
                        └──── 返工 ◀─────────┘

任意非终态 ──▶ 阻塞 ──▶ 回退到进入前的状态
```

**「已验证」独立成态**，是为了让「形式有效是实质验收的前置」**由结构保证**：

```
已交付 ──verify──▶ 已验证 ──accept──▶ 已验收
```

`accept` **只可能来自已验证**。于是「未校验即验收」在结构上不可达。

| 动作 | 判什么 | 谁发 |
|---|---|---|
| `verify` | **形式**：证据齐否、路径存在否、门禁退出码为 0 否 | TL 或 commander |
| `accept` | **实质**：逐条比对验收标准 | PM |

**需求与任务共用同一个编号。** 需求在**定稿那一刻**升级为任务，编号不变。
好处：结构上不可能出现「需求翻牌了但任务不见了」。

## 三、动词

**一切状态变更只经这 29 个动词。** 手工编辑状态文件**不是**流程的一部分。

### 3.1 条目

| 动词 | 谁可发 | 前置状态 | 作用 |
|---|---|---|---|
| `register` | 任何人 | — | 登记；**编号当场原子发放** |
| `claim-analyze` | PM | 登记／阻塞 | 认领分析，记认领人 |
| `define` | PM（须为认领人） | 分析中 | 落四要素；升级为任务；**清空认领人**（交接面） |
| `freeze` | PM／TL／commander | 已定稿 | 固化范围与验收的快照 |
| `claim-dev` | TL | 已定稿且**就绪** | 认领开发 |
| `start` | TL（须为认领人） | 已认领 | 开工 |
| `deliver` | TL（须为认领人） | 开发中 | 记证据（提交／门禁／路径）；**不产生 ✅** |
| `verify` | TL／commander | 已交付 | **形式校验** |
| `reverify` | TL | 已交付／已验证 | 返工；**轮次 +1，失败轮次保留** |
| `accept` | PM | **已验证** | 实质验收 → ✅ |
| `block` | TL／PM／PO／commander | 非终态 | 阻塞，记原因与进入前状态 |
| `unblock` | 同上 | 阻塞 | **回到进入前的状态** |
| `set-priority` | PO／commander | 非终态 | 定 P0／P1／P2 |
| `complete` | OPS | 非终态 | OPS 线自主闭环 |
| `review` | DBA | 非终态 | 评审即入库 |
| `override` | commander | 任意 | **唯一的强制转换**；必须给理由，进事件流 |

### 3.2 资源

| 动词 | 作用 |
|---|---|
| `acquire` | 申请租约；配额满时**先即时回收**再排队 |
| `release` | 显式释放 |
| `reclaim` | **执行层回调**（真正 DROP 之后调用）；因元数据锁失败则加标记 |
| `leases` | 只读：用量与可回收清单 |

### 3.3 合并

| 动词 | 作用 |
|---|---|
| `merge-request` | 显式触发；过六闸 |
| `merge-next` | 取队首；**串行闸**——已有合并在进行即拒 |
| `merge-ok` | 记结果提交 |
| `merge-conflict` | **冲突即拒**，转动作项给 TL；**永不自动解冲突** |
| `merge-status` | 队列可见面 |

### 3.4 只读

| 动词 | 回答的问题 |
|---|---|
| `ready` | 某线某角色现在能认领什么（按优先级排序） |
| `trace` | **正查**：这条目凭什么算完成？谁验的？ |
| `why` | **反查**：这个文件为什么是这个样？谁授权的？范围是什么？ |
| `audit` | 有哪些异常（**通过项静默**） |
| `report` | 人读报告（**只列异常与待决**） |
| `status`／`health` | 一行摘要／自检 |
| `publish` | 渲染视图 → 显式路径提交 → 事件快照 |

## 四、不变量（协调器强制，不是靠自觉）

**一·编号唯一。** 发号与登录取号在**同一次持锁事务**内完成，撞号在结构上不可能。

**二·一条目一认领人。** 后来者被**拒绝**，不是"自行避让"。

**三·状态单向。** `✅` 不可倒回；未终态的转换不得跳过中间态。
「未校验即验收」「未定稿即交付」在结构上不可达。

**四·分权。** 每个动词有允许的角色集；越权**拒绝**。

**五·界内。** 实际改动必须落在条目白名单内——**交付时与合并时各判一次**。

**六·乐观并发。** 请求须带**期望版本号**；不符即拒并返回当前快照。
**这是治「陈旧视图」的那一条**——旧机制下两个会话可以先后读到同一状态再各自写，
于是产生了一批「竞态／重试」提交；版本号让过期的一方**必然失败**。

**七·就绪判定。** 认领开发前，协调器算：

```
就绪(dev, 线) =
      状态 == 已定稿
    ∧ 前置全部终态
    ∧ 认领人为空
    ∧ 白名单 ∩ 所有在办条目的白名单 == ∅     ← 从纪律变成函数
    ∧ 该线在办数 < 线内预算
    ∧ 优先级已定
```

**「白名单互不重叠」不再靠自觉**——它由协调器算出。TL 派单前只查可认领清单。

**八·审计读真实文件。** 审计工具读**磁盘上的视图**，不读协调器的内存或缓存——
否则就成了「自己证明自己」。

## 五、四要素

**无白名单不成条目。** 定稿必须四要素齐，**缺一即拒、状态不变**。

| 要素 | 要求 |
|---|---|
| **修改范围白名单** | 非空 |
| **不动清单** | 显式声明；空列表合法（＝明确声明"无"） |
| **前置** | 允许为空（＝无前置）；引用必须存在，且**不得成环** |
| **验收标准** | 非空，且**结构化**（见下） |

**验收标准必须结构化**——这是本体系最值钱的一处：
它让「回标必须带实证」从一条纪律变成**可校验条件**。

```
acceptance:
  - type: test       cmd: "<门禁命令>"             expect_exit: 0
  - type: negative   desc: "未注入仍 200 ⇒ 必红"
  - type: evidence   path: "worktrees/T-D-194.SUBMISSION.md"
```

| 类型 | 判据 |
|---|---|
| `test` | 命令退出码 = 期望值 |
| `negative` | 描述必须有——**无负例的验收不算验收** |
| `evidence` | **路径存在且可读** |
| `manual` | 只记描述；**不可交给机械校验** |

**认领即冻结**：范围／验收／口径以**认领那一刻的快照**为准，此后改动**一律走新条目**。

## 六、编号

| 项 | 规则 |
|---|---|
| 形态 | `类型-线码-N`，**线内独立计数**（`T-D-194`／`R-ACL-67`／`OPS-162`） |
| 发放 | **一律经协调器**，原子发放——**禁手工自选号** |
| 迁移件 | revision 以主干**迁移目录**（见绑定 §迁移）当前最大号为基准自增 |
| **串行族** | **同时只允许一个在飞占号**（`pending`），落物或让号后才放下一个 |

**为什么迁移件要串行**：它的**号顺序就是链位顺序**。
两个件同时占号、各自把父节点接到当时的 head 上，合起来必然**分叉成两个 head**——
升级目标不唯一。所以迁移的收口有三处，**放号是第一处**：

| 收口点 | 谁执行 |
|---|---|
| 放号 | 协调器（串行族闸，`E_NUMBER_INFLIGHT`） |
| 提交 | `tools/commit_gate.py`（含迁移链腿） |
| 合并 | `merge.py` 链位闸（判据与提交闸**同源**） |

判据只有一处实现：`coordinator/bg_coordinator/migrations.py`。

**由此消失的一整类问题**：号段空洞、真脱同步、待回填——
它们全是**并发写簿记**的产物，簿记被原子发号取代后不再存在。

## 七、移交

| 场景 | 怎么做 |
|---|---|
| **跨线移交** | 以 `register` 登记到**目标线**。发送方**不做状态变更**——不预标、不预翻牌 |
| **移交运维** | 拆 OPS 条目，含 runbook 要点 ＋ 前置 ＋ 验收口径 |
| **移交数据库** | 迁移类条目：DBA 评审通过即入库；DDL 执行归 ops |
| **不属于自己的改动** | 立条目或报批，**不直接动手** |

**发送方不预翻牌的理由**：接收线按「待处理」筛选待办。
预翻牌会让**整条被扫描漏过**——历史上出现过，靠用户点名才发现。

**OPS 例外**：OPS 线无 PM。任务交到 ops 即由 **ops 自主闭环**（执行、留痕、终态自理），
**不等 PM 对账**；以某条 OPS 条目为前置的角色**自行查看**其状态，ops 不承担通知义务。

## 八、记录格式

**事件**（只追加）：

```json
{
  "seq": 10241, "ts": "2026-10-04T12:00:00Z",
  "verb": "define", "id": "T-D-236", "actor": "pm-D",
  "before": {"status": "analyzing", "ver": 3},
  "after":  {"status": "defined",   "ver": 4},
  "expect_ver": 3, "request_id": "uuid-…", "result": "ok",
  "detail": {}, "snapshot": { }
}
```

`before`／`after` 是**语义摘要**（给人看、给报告用）。
`snapshot` 是**完整条目快照**——保证状态缓存丢失后能**逐字重建**。

**条目**（状态缓存的元素）：

```
id  kind  line  status  title  src
deps[]  owner  definer  acceptor
whitelist[]  frozen[]  acceptance[]
priority  evidence[]  changed_files[]
round  ver
blocked_from  block_reason  frozen_snapshot
```

| 字段 | 作用 |
|---|---|
| `deps[]` | **依赖图**——取代自由文本的「前置」 |
| `owner` | 当前认领人；**定稿时清空**（交接面） |
| `definer`／`acceptor` | 定稿人与验收人；两者应为同线同一 PM |
| `priority` | **PO 的产出落点**——未定优先级不得派工 |
| `evidence[]` | 每轮交付一份；**失败轮次保留**（它们是溯源的一部分） |
| `round` | 返工轮次；`accept` 只认最新轮 |
| `ver` | **乐观并发的比对依据** |
| `frozen_snapshot` | 冻结那一刻的范围与验收快照 |

**退回**：被拒的动作**也写一条事件**（`result` 记拒绝码）。
报告里的「异常」节由这些拒绝与审核异常构成——**通过项静默**。

## 九、上下文纪律

**上下文是稀缺资源，与子代理额度同级。** 本节把「怎么读」定死。

### 9.1 现状的教训（实测）

| 面 | 实测规模 | 问题 |
|---|---|---|
| 线板（单线） | **208k tokens** | **超过任何可用上下文窗口** |
| 线 inbox（单线） | 116k tokens | 同上 |
| 总账 | 52k tokens | 读一次即占满大半 |

**这不是"读起来慢"，是根本读不下**——代理要么截断、要么根本没读。

**根因**：证据无处可去，只能内联进状态表格的单元格里。
一格塞进整段事故记录、整轮评审过程、成串 commit——**状态表被当成了案卷柜**。

### 9.2 四条规则

**其一·读命令必须有界。** 任何读命令的默认输出必须有**条数上限**与**字段宽度上限**。
超限即折叠，并显式告知「另有 N 条」。要看全部，必须显式请求。
**默认给结论，全量是例外。**

**其二·明细按需取，不做批量预读。** 谁需要详情，谁发起一次有界查询；
**不把明细预加载进任何人的起始上下文**。

**其三·投影只渲染载荷字段。** 任务视图渲染的是**载荷**（编号、状态、认领人、白名单、验收条数），
**不是案卷**。证据与经过住在事件记录里，从投影里出去。

**其四·一条长文案不许独占上下文。** 任何字段显示超过宽度上限即裁剪。

### 9.3 实测效果

协调器的读命令都带默认上限——`trace` 出尾部 12 条、`why` 最多 5 条匹配、
异常行裁剪到 80 字。实测输出：

| 命令 | 输出规模 |
|---|---|
| 正查单条 | **897 字符** |
| 人读报告 | **1256 字符** |
| 反查单文件 | **248 字符** |

这是数量级的差别——**「状态不炸」与「查询也不炸」是两件事**。

### 9.4 记录增长

事件**只追加**，每条事件携带**完整条目快照**——这是为了「状态缓存丢失后能逐字重建」。

**代价**：事件日志的增长**快于状态变化数**（每条事件都嵌一份完整条目）。

**缓解**：事件日志在仓库之外，不进上下文；
按需定期归档为**全量快照 ＋ 增量**，归档后不再逐条重放。
**该代价已知且可接受**——它是「可重建」换来的。
