# RISKS.md — 新版设计的风险

> **只审本设计自身**。不讨论被本设计替代的旧机制。
> 每条给：风险、场景、结构成因、处置。处置只有三种结局——**设计可解**、**必须接受**、**靠外部控制**。

---

## 一、权威层：双份落点可能分叉

### R1 🔴 事件日志与状态缓存不一致

**设计现状**：事件日志**只追加**、是权威；状态缓存可重算。但写入是**两步**——先追加事件，再写缓存。

**风险**：两次写之间崩溃 ⇒ 缓存落后于日志。更隐蔽的是**读路径只读缓存、从不校验**——
于是「权威」在事实上退化成缓存，而日志的权威地位**没有任何机制保证**。

**处置（设计可解，优先级最高）**：

1. **缓存只由日志派生**——写入路径不直接写缓存，改为「追加事件 → 从日志重放到当前位置 → 落缓存」；
2. 或缓存带 `last_seq`，读时若与日志末尾不符即重放；
3. 提供 `verify` 动作：比对缓存与重放结果，不一致即报异常。

**判据**：缓存与重放**逐字相等**才允许用它。

---

## 二、可用性

### R2 🔴 协调器是任务写入的单点

**风险**：协调器不可用 ⇒ **任务写入停摆**。而代码工作仍在继续 ⇒
**产出无法登记、交付无法记录**，系统进入「事实已发生、记录跟不上」的状态。

**处置**：

1. **接受**：单点是集中化换来的，不可消除；
2. **缩小爆炸半径**：读路径**不取锁**——协调器写不了时，读（报告、可认领、审计）**仍然可用**；
3. 状态在磁盘且可重建；
4. **降级口径必须写死**：不可用时，代码工作继续，**任务写入排队**；
   恢复后按事件顺序补录，**补录也走动词**（不是手工改文件）。

### R3 🟠 状态根的持久性

**风险**：状态根在仓库之外 ⇒ **不受 git 保护**。一次磁盘故障即丢失全部任务史。

**处置**：发布时**同批把事件快照进仓库**（已在设计中）＋ 保留最近若干份 ＋ **定期恢复演练**。
**恢复演练不是可选优化**——没有演练过的备份不算备份。

---

## 三、写权边界

### R4 🔴 直接编辑绕过协调器

**设计现状**：投影是渲染产物；检测到直改后**覆盖并留痕**。

**风险**：协调器**无法阻止**一次已经发生的文件编辑。更严重的是——
**视图看起来是权威的**，被改过的视图会让人基于错误信息行动。

**处置（必须接受，但可削弱）**：

1. **接受**：这是"唯一写者"模式的固有边界——只要文件在磁盘上可写，就能被写；
2. **削弱**：投影头部带**发布时间与序号**；客户端发写请求带**自己读到的序号**，
   不匹配即拒——**基于陈旧视图的写请求会失败，而不是成功**；
3. **削弱**：直改命中即为**异常**，进报告；
4. **削弱**：**评审与门禁只信任协调器状态**——视图不承载任何"只有视图才有"的信息，
   于是改了视图也拿不到好处。

### R5 🟠 协调器自己也在往主干写

**风险**：协调器写视图到主干，而开发分支也在写主干 ⇒ 提交竞争。

**处置**：

1. 协调器**只提交视图路径**（显式路径，不带代码）——已在设计中；
2. 批量提交 ＋ 非快进重试；
3. **边界**：视图提交**永不携带代码改动**。违反即事故。

---

## 四、状态与现实的差距

### R6 🟠 投影延迟 ⇒ 读到陈旧视图

**风险**：视图按节拍渲染。节拍之间，事务已提交但视图未更新。
基于陈旧视图做决策，可能重复认领（**会被乐观并发拒绝**）或按旧标准工作。

**处置**：

1. 发布节拍要短，关键动作后**强制发布**；
2. 投影头部的序号是**读侧的一致性锚**——客户端带序号写，过期即拒；
3. **可观测**：报告标注快照点，让"审计说没问题"不被误读为 live 没问题。

### R7 🟠 协调器状态与代码真实状态不一致

**风险**：条目被标为已交付，但代码并未真的在主干上；
或代码已合并，而条目仍是开发中。**两类漂移都会发生。**

**结构成因**：任务状态与 git 是**两套独立的事实**，没有任何机制强制它们同步。

**处置**：

1. **合并闸校验**：合并请求必须带**提交**，且该提交的改动文件落在白名单内；
2. **审计腿**：已交付状态的条目，其声明的提交必须在主干可达——不可达即异常；
3. **接受**：两套事实无法完全对齐，**但漂移必须可见**。

---

## 五、记录随时间增长

### R8 🟠 事件日志增长快于状态变化

**设计现状**：每条事件携带**完整条目快照**——为了"缓存丢失后能逐字重建"。

**风险**：日志增长速度 **= 变化数 × 条目数 × 快照大小**。
日积月累后，**重建变慢**，且快照会成为新的体积问题。

**处置**：

1. **定期归档**：全量快照 ＋ 之后增量；重建从最近快照起，不从头重放；
2. 归档件**不进上下文**——它是重建用的，不是给人读的；
3. **接受**：这是"可重建"的代价，**已知且值得**。

### R9 🟠 快照嵌入的隐私面

**风险**：快照里嵌入了条目的全部字段。若某字段含敏感内容（凭据、账号、内网地址），
它会**随事件一起落到状态根**，而状态根在仓库之外、**不受 git 的忽略规则保护**。

**处置**：**明确禁止在条目字段里写凭据**——与日志纪律同源。
审计腿检查明显形态的敏感串。

---

## 六、新机制的首次落地

### R10 🔴 新角色与新流程从未被验证过

**风险**：同时引入**两个新角色**、**一套新流程**、**一个新工具**。
三者一齐上，失败时**难以归因**——不知道是角色定义有问题、流程有缺口，还是工具有缺陷。

**处置**：

1. **单线试点**：先在一线跑通全链，再铺开；
2. **切换开关**：新流程可整体关闭，退回旧机制（旧机制**保留只读**，不删）；
3. **可见的验收点**：试点要给出「全链走通」的实证 ——
   登记 → 分析 → 定稿 → 认领 → 派单 → 交付 → 校验 → 验收 → 合并，**一次不落**。

### R11 🟠 新旧并存期的双重记账

**风险**：过渡期若部分会话用新流程、部分用旧流程，
**同一件事会有两份记录**，且**互不知道对方**。

**处置**：过渡期必须**定死一个权威**。
建议：**以协调器为准**；旧文件冻结为**只读归档**，不再接受写入。

---

## 七、人的界面

### R12 🟠 可见性下降

**风险**：不再有人手写看板 ⇒ 「扫一眼看板就知道现状」这个习惯消失。
**报告的受众面比看板窄**——看板是人写的，报告是生成的；后者信息密度可控但**不一定会被读**。

**处置**：

1. 报告的**第二节「需要你决定」**是给人看的核心——要保证它**真的只列待决**；
2. 报告为**覆盖写**，靠 git 保留历史；人是通过 git 看演变的，**这一点要写进使用习惯**；
3. **接受**：可见性从"人人可见的文件"变成"一份报告 ＋ 按需查询"，**这是取舍，不是纯收益**。

## 八、汇总

| R1 | 事件日志与缓存分叉 | **设计可解**（缓存只由日志派生） |

| R3 | 状态根持久性 | 设计可解（快照进仓库 ＋ 恢复演练） |
| R4 | 直接编辑绕过 | **必须接受** ＋ 序号锚 ＋ 评审只信协调器状态 |
| R5 | 协调器也往主干写 | 设计可解（只提交视图路径） |

## 九、最需要先解决的两条

**R1 与 R10。**

**R1** 是设计缺陷，且**已经存在于实现里**——权威与缓存的地位没有机制保证。
它不解决，前面积累的所有状态纪律都建立在流沙上。

**R10** 是落地风险，且**无法靠设计消除**——只能靠试点与实证。
在它被消化之前，**不铺开**是唯一正确的选择。
