## 1. 设计目标与不变量

### 1.1 三个待解问题

| 问题 | 实测证据 |
|---|---|
| 共享文件写竞争 | `todo/` 相关提交 **4268**；近 40 条提交 **40/40** 触及 `todo/`；含「竞态／重试」提交 **82** |
| 合并仪式过重 | 近 80 条合并中 `pm/*` : `dev/*` = **19 : 2**（**80% 是为 `todo/` 打的**） |
| 资源枯竭 | 128 个 worktree 目录；scratch 库靠手动回收；MDL 残留曾致库长期占用 |

**根因**：`todo/` 的 markdown 表格是**"直读"逼出来的编码格式**——把结构化字段（状态、依赖、白名单、验收）压进一行文本。为维持这种编码，公约里累积了一整套加固纪律：

| 现有纪律／机制 | 存在的原因 |
|---|---|
| C9 线板白名单写法（反引号成对、`/**` 外禁 `*`、7 格、状态格首字符） | 文本表格会被写坏 |
| C8 inbox 表结构（表头↔分隔行间距 0） | markdown 渲染锚点 |
| C3 状态字段合法性（四 token 枚举） | 机读只能靠 token |
| 转义感知切分（`\|` 是内容） | 竖线既是分隔符又是内容 |
| `precommit` 删除守护腿 | 多会话以陈旧副本整档重写（实证 R-D-178） |
| `registry.md` 号段空洞／待回填／脱同步三分类 | 并发写簿记 |

### 1.2 不变量（一律不变）

| 项 | 出处 |
|---|---|
| ~~`process_audit`／`alloc_number --check` 继续读真实磁盘文本~~（**已废止**：本体系自持判据，不再消费外部件；见文首自持纪律） | 防自证闭环 |
| `git add` 只加自己改的路径，严禁 `-A` | 公约 2 |
| 主 checkout 只做对账与合并，不在其内开发 | `agents/commander.md` |
| 子代理永不 merge／push、不标 ✅ | 公约 13⑥ |
| 交付即冻结，新缺口开新条目 | 公约 9 |
| `✅` 只由交付方写 | 公约 1 |
| 单对话累计子代理 ≤ 10（含已终止；续派不计数） | 公约 13⑧ |
| 闸一（共享文件）／闸二（触库并发） | 公约 13④ |

### 1.3 核心设计原则

> **协调器只执行动词，不做决策。**
> 所有判定规则住在配置与标准里，协调器只做校验与串行化——否则它变成无人能审计的黑箱。

> **"现在是什么"归协调器；"曾经发生过什么"归 commit。**
> 这两个问题不该挤在同一份 markdown 表格里。

## 2. 角色设计

### 2.1 角色表

| 角色 | 形态 | 归属 | 派单权 | 工作面 | 硬禁止 |
|---|---|---|---|---|---|
| **commander** | 独立会话 | 用户 | ✅ | 用户接口、git worktree／分支／推送、主 checkout 守护、**业务合并**、仲裁 | 不碰业务代码；不在主 checkout 开发 |
| **PO** | 独立会话 | 用户 | ✅ **派 PM** | 跨线优先级排序、资源与范围冲突仲裁、总积压盘点 | 不做需求分拣；不派 dev；不碰 git |
| **PM** | **子代理** | **PO** | ❌ | 本线需求 → 条目定义（白名单／不动／前置／验收）；**验收** | 不写实现代码；不派单 |
| **Tech Lead** | 独立会话（每线一个） | 用户 | ✅ **派 dev** | 认领已定稿条目、派 dev、独立重跑门禁、发起合并 | 不碰验收；不自拟范围（纪律 11） |
| **dev** | 子代理 | TL | ❌ | 实现 ＋ 测试 ＋ 门禁 | 永不 merge／push；不改任务数据 |
| **OPS** | 独立会话·亲办 | 用户 | ❌ | 部署、迁移窗口执行、巡检、容量 | 不改业务代码；不改 DB 实例参数 |
| **DBA** | 独立会话·亲办 | 用户 | ❌ | 迁移评审闸、实例运维（备份／恢复／容量／授权） | 不执行生产 DDL（归 ops） |

**三条链无交叉**：PO 派 PM（分析）、TL 派 dev（执行）、commander 做业务合并。
**PM 与 TL 之间没有派单关系**，只靠「已定稿条目」这一个交接面。

**同构映射**：commander＝工程经理 · PO＝产品负责人 · PM＝各线产品 · TL＝各线技术负责人 · dev＝工程师 · OPS／DBA＝SRE／DBA。

### 2.2 派单权与额度

| 会话 | 额度 10 的分配 |
|---|---|
| **PO** | 6 条线 × 1 PM ＝ 6（**按线复用**，不按需求新开），余 4 备用 |
| **TL（每线）** | dev ＋ verifier 约 8（`send_message` 续派**不计数**） |

**结论：整图在 ⑧ 上限 10 之内跑得通，不需改额度。** 前提是监视器不落 LLM（见 §7）。

### 2.3 协调器与特权段正交（重要澄清）

| | 问题 | 答案 |
|---|---|---|
| 甲 | 协调器**自己**要不要特权来写任务数据？ | **不要**——任务数据在工作区内，普通写权限 |
| 乙 | 协调器要不要替 OPS／DBA**执行特权动作**？ | **不要，也不该**——那是 ops 面 |

**实证**：`todo/` 与 `todo/inbox/OPS.md` 均 `test -w` 通过；`AGENTS.md:36` 原文约束的是「子代理**工作区沙箱够不着特权段**」（**路径**约束，非目录约束）；文档中真实拒写案例是 `tqsdk` 写 `/root/.tqsdk`，与任务数据无关。

**正确姿态**：协调器**保持最小权限（workspace-write），永远不碰特权段**——不 `systemctl`、不 rsync `/opt`、不执行 DDL。它只**记录**「ops 已完成 X」；**「完成 X」是 ops 自己做的**。

给协调器特权域不是"解决可达性"，而是制造一个**所有角色都能触达的特权写者**。OPS-28 的约束依然成立，但与协调器**正交**。

### 2.4 纪律 ⑥ 需要改写

现行 ⑥「子代理永不改 `todo/`」与「PM 是子代理、职责就是 `define`」直接冲突。

**改写为**：**「子代理只能经协调器写，禁止直接碰任务数据文件」**。
与原意图（防越权、防并发写）完全一致，且**比原条款更强**——协调器能做 ⑥ 做不到的校验（白名单、状态单向、`expect-ver`）。

## 3. 事件流转

### 3.1 端到端流程

```
① 需求登记   ← register（任何人，含 PO）
② PM 分析    PO 派 PM 子代理      ← claim-analyze + define（四要素齐，缺则拒）
③ 定稿落地   线板 [未处理]        ← freeze（TL 可即认领）
④ TL 认领                        ← claim-dev
⑤ TL 派 dev  TL 子代理            ← deliver（记 commit＋门禁实证，不标 ✅）
⑥ 机械校验   TL／协调器           ← verify（证据齐、路径在、退出码 0 ⇒ verified）
⑦ 验收       PO 派 PM 子代理      ← accept（非 PM 拒）
⑧ 合并       TL／commander 显式触发 ← request_merge（六闸）
```

**派单点只有两处**：PO 派 PM、TL 派 dev。
**⑤→⑦ 之间必须过 ⑥**：交付不等于可验收——**形式有效是实质验收的前置**（见 §4.9.3）。

### 3.2 动作集（全部带 `expect-ver`）

| 动作 | 谁做 | 前置状态 | 后置 |
|---|---|---|---|
| `register` | 任何人（含 PO） | — | registered，发号锁 |
| `claim-analyze` | PM | registered／blocked | analyzing，owner=PM |
| `define` | PM | analyzing | defined；**四要素齐，缺则拒**；R→T |
| `freeze` | 协调器自动 | defined | 快照冻结 |
| `claim-dev` | TL | defined 且 ready | claimed |
| `start` | TL | claimed | in_progress |
| `deliver` | TL（代 dev） | in_progress | delivered，只记证据 |
| `verify` | TL | delivered | verified（**协调器机械校验**：证据齐、路径在、门禁退出码 0） |
| `reverify` | TL | verified 失败回退 | in_progress（**返工**，`round` +1） |
| `accept` | PM | verified | accepted（✅），不可倒回 |
| `block`／`unblock` | 协调器／TL | 非终态 | blocked ↔ 原状态 |
| `complete` | OPS | — | OPS 自主闭环 |
| `review` | DBA | — | 评审即入库 |
| `override --reason` | 受限角色 | 任意 | 留痕逃生口 |
| `acquire_slot`／`release_slot` | dev／test | — | 资源租约（§5） |
| `request_merge` | TL／commander | delivered | 入合并队列（§6） |

**全部动作在锁内 read-modify-write，全程互斥。**

### 3.3 就绪判定

```
ready_for(role, line) =
      status == defined
    ∧ deps 全部终态
    ∧ (role == dev → owner 为空 ∧ whitelist ∩ 所有在办条目的 whitelist == ∅)
    ∧ (role == pm  → owner 为空 ∧ 未被认领分析)
    ∧ line 在办数 < 线内预算
    ∧ priority 已定
```

**「白名单互不重叠」从一条纪律，变成可判定函数。**
同时免费获得：互斥锁（一条目一认领人）、幂等判定（不重复处理）、`ver` 比对（确认未被抢）。

### 3.4 事件记录（协调器的唯一权威落地物）

**每次动作产生一条不可变事件**：

```json
{"seq": 10241, "ts": "2026-10-04T12:00:00Z",
 "verb": "define", "id": "T-D-236", "actor": "pm-D",
 "before": {"status": "analyzing", "ver": 3},
 "after":  {"status": "defined",  "ver": 4},
 "expect_ver": 3, "request_id": "uuid-...", "result": "ok"}
```

| 性质 | 说明 |
|---|---|
| **append-only** | 永不改写。**就地编辑 = 事故**（状态机被静默污染且不可重建） |
| 幂等 | `request_id` 去重，重试不产生重复事件 |
| 可重放 | `state.json` 由事件重放得出，崩溃后可完整重建 |
| 落点 | 仓库之外（§4.2） |

**为什么在工作区根而不在仓库内 `var/`**：仓库内任何路径都可能被 `git clean -xfd` 清掉；工作区根**不在 git 对象面内**，天然免疫。且它不在任何 worktree 里 ⇒ **worktree 副本这个变量彻底消失**。

### 4.3 存储格式：不再需要"可解析"

**现状**是把结构化字段编码进 markdown 行。**协调器接管后，存储格式就是数据本身**：

```
{ id, kind, line, status, deps[], owner, definer, acceptor,
  whitelist[], frozen[], acceptance[], evidence, priority, ver, events[] }
```

其中 `acceptance` **不是散文**，而是结构化断言：

```
acceptance: [
  { type: "test",     cmd: "pytest tests/... -k ...", expect_exit: 0 },
  { type: "negative", desc: "未注入仍 200 ⇒ 必红" },
  { type: "evidence", path: "worktrees/<id>.SUBMISSION.md" }
]
```

**这才对**——「回标 ✅ 必须带实证」**从一条纪律变成一个可校验条件**。格式松绑真正值钱的地方在此：不是为了少写竖线，而是让原本只能写在散文里的东西**终于可被机器判定**。

### 4.4 视图 A：兼容视图（保现有工具零改造）

**markdown 从"可解析的双向账本"降为"单向渲染"。** 单向就不需要可解析，只需可读。

（历史）当时为了让既有 **290 处路径引用**（62 个文件）一行都不改，渲染器先装成旧格式——这部分外部件如今**已不在本体系的依赖面内**（见文首自持纪律），兼容视图只作为**人读形态**保留：

| 必须保住 | 为什么 |
|---|---|
| 7 格、未转义竖线、`\|` 转义 | C9 机读 |
| 状态格**首字符**是 token（`[未处理]`／`[处理中]`／`✅`／…） | C3 归类 |
| 表头↔分隔行间距 0 | C8 |
| 白名单反引号成对、`/**` 外无 `*` | C9 |

**过渡期接受新老状态的映射损失**（`已定稿` 与 `已交付` 都映射到 `[处理中]`），这与现状一致，非回归。

**等读者全部切到协调器 API 后，渲染器再简化**——那时 7 格与 token 都可以不要。

### 4.5 视图 B：定时人读报告（新增，一等公民）

**与兼容视图是两份东西**：

| | 兼容视图 A | 报告视图 B |

| 格式约束 | 必须精确兼容 | **自由** |
| 目的 | 不破坏现有门禁 | **让人一眼看懂现在怎么了** |

| T-D-236 | 验收标准有歧义 | 4h | 见下 |

**节次理由**：

- 第五节让资源枯竭**在发生前可见**；
- 快照点标注把**审计滞后**如实写给人看。

**发布节拍**：显式 checkpoint（立项／验收／合并后立即）＋ 定时（建议 **30~60 秒**，可配）。
报告为**覆盖写**（同一路径，靠 git 保留历史），不累积文件。

### 4.6 发布节拍与审计滞后

| 环节 | 设计 |
|---|---|
| 触发 | 显式 checkpoint ＋ 定时 |
| 动作 | state → 渲染视图 A＋B → `git commit -- todo/ reports/` → 记 `published_rev` |
| 提交粒 | **一次投影一次提交**（不重放逐条事件，否则提交风暴） |
| 一致性 | 视图与 `published_rev` **同提交**落地 ⇒ 读者拿到某一刻的一致快照 |

**审计滞后是甲案的明确代价**：
- ✅ 不破自证闭环（审计读真实磁盘文本，非协调器内存）
- ⚠️ 投影发布前，新条目对审计**不可见**

**缓解**：缩短间隔；关键动作后强制发布；**在报告第六节显式标注快照点**，让"审计说没问题"不会被误读成"live 没问题"。

### 4.7 events 的持久性（不可省）

`events.jsonl` 在仓库之外 ⇒ **一次磁盘故障就丢了全部任务史**。

**缓解（甲案的必要组成，非可选优化）**：
1. 每次发布同批把 events **快照进仓库**（如 `todo/.coordinator-snapshot/events-<rev>.jsonl`）
2. 保留最近 N 份（建议 N＝10）
3. 定期做**恢复演练**（从快照重建 state 并比对）

### 4.8 架构副产物：四份账塌缩为视图

甲案下 `board.md`／`lines/*`／`inbox/*`／`registry.md` 是**同一状态的不同渲染**。
现状的"总账／线板／inbox 三层"是**人工分账的产物**，不是需求。

**结果**：「inbox 翻牌 与 线板立案 要同步」这条纪律**自动消失**。

### 4.9 审核与溯源（**协调器的一等能力**）

> **反模式（必须消除）**：把 14 项审计的原始数字、61 份 SUBMISSION 路径、1054 行线板抄进报告给人看。
> **那还是"把所有文档又丢过来"**，只是换了个容器。
> **正确形态**：协调器**自己跑审核、自己留证据链**，**只把异常与需要决定的事递给人**。

#### 4.9.1 溯源：证据链是一等数据结构

现状：一条条目的证据散在 **4 处**——`worktrees/<id>.SUBMISSION.md`（61 份）、commit、原始日志（如 `scratch-TD*.log`）、markdown 表格里的散文格。**要复原一条链全靠人工侦探。**

协调器把证据链变成**结构化的有向链**：

```
T-D-194 证据链
├─ define     pm-D      2026-10-04T09:12Z  ver 3→4   验收标准 4 条
├─ claim-dev  TL-D      2026-10-04T09:20Z  ver 4→5
├─ deliver    TL-D      2026-10-04T11:40Z  ver 5→6
│   ├─ commit      de1f3a2
│   ├─ gate        pytest -q … → exit 0（2182 passed）
│   ├─ evidence    worktrees/T-D-194.SUBMISSION.md（inode/sha 留痕）
│   └─ verifier    verifier-3 独立复跑 → exit 0
├─ verify     TL-D      2026-10-04T11:52Z  ver 6→7   形式有效
└─ accept     pm-D      2026-10-04T12:05Z  ver 7→8   4/4 验收项逐条过
```

**两个方向的查询都要支持**（现状两个方向都得人工拼）：

| 方向 | 问题 | 现状 |
|---|---|---|
| **正查** | 这条目凭什么算完成？谁验的？ | 翻 4 处 |
| **反查** | 这个文件／commit 为什么是这个样？谁授权的？范围是什么？ | **几乎做不到** |

反查的价值被低估：`git blame` 只能给出 commit，**给不出"当时的范围与验收标准"**。协调器一条查询即可回答。

#### 4.9.2 审核：从"全局报全量"改为"按条目筛异常"

现状 `process_audit` 是**全局检查**，输出**全量**（C1~C14，其中 C8~C14 默认只出 WARN）。**读的人要自己从全量里挑出与自己相关的。**

协调器改为**在动作提交点做按条目检查**，**只产异常**：

| 检查 | 时机 | 通过 | 失败 |
|---|---|---|---|
| 状态合法性 | 每次动作 | 静默 | 拒绝该动作 |
| 白名单非空、验收标准非空 | `define` | 静默 | 拒绝 |
| 前置均已终态 | `claim-dev` | 静默 | 拒绝 |
| 证据路径存在且可读 | `deliver` | 静默 | 拒绝 |
| 门禁退出码 = 0 | `deliver` | 静默 | 拒绝 |
| 白名单与实际改动文件一致 | `request_merge` | 静默 | 拒绝 |
| 迁移件是否已评审 | 定时 | 静默 | **升级到 DBA 监视** |
| 孤儿授权／schema 漂移 | 定时 | 静默 | **升级到 DBA 监视** |

**规则**：**通过 ⇒ 什么都不说；失败 ⇒ 一条带责任人的异常。**

#### 4.9.3 审核流水线（三级，人只在第三级）

```
① 协调器·机械校验   —— 形式有效：证件齐否、路径在否、退出码 0 否
② TL／verifier·独立复核 —— 对抗复核：独立复跑门禁、专找假绿
③ PM·实质验收          —— 逐条比对验收标准
```

**边界必须钉死**：

> **协调器只做"形式有效"，绝不做"内容正确"。**
> 它能判"门禁跑了且退出码 0"，**判不了"这个测试是否真的证明了这个功能"**。
> 机械通过 **≠** 实质正确——混淆二者就是制造假绿。

#### 4.9.4 报告只出现异常

| 节 | 内容 | 不出现 |
|---|---|---|
| 需要你决定 | 人工闸（歧义、超范围、争议） | — |
| 异常 | 审核失败项 ＋ **责任人** ＋ 建议动作 | **通过项**（全部静默） |
| 阻塞 | 卡住条目与原因 | — |
| 在办 | 正常进行中的条目（一行一条） | — |
| 审计摘录 | **仅**「本期 N 条正常，0 条异常」＋ 快照点 | 14 项数字明细 |

**14 项审计数字不再进报告**——它们该由协调器**自己消化成异常**。要看明细的人，去问协调器。

#### 4.9.5 溯源的一个真实难点：返工破坏了"不可变"

若允许 `deliver → 返工 → deliver`，同一 `id` 会出现**多条证据**。朴素实现会让"哪条是最终证据"变成新的侦探工作。

**处置**：引入 `round`（轮次）。证据链记录 `(id, round, ...)`；`accept` 只认**最新轮**且**所有轮次的历史都保留**（失败的轮次也留，它们是溯源的一部分，不是垃圾）。

#### 4.9.6 协调器判不了"证据是真的"

机械校验**验证不了证据的真实性**——它可以查路径存在、退出码为 0，**查不出有人在日志里做了手脚**。

**这一层只能靠 ② TL 独立重跑 ＋ ③ verifier 对抗复核。** 协调器不是审计的终点，是**审计的入口与索引**。

## 5. 资源管理
### 5.1 枯竭链（实测）

```
测试异常退出 → ①scratch 库残留 → ③MDL 残留（DROP 被未关闭事务挂住）
   → 实例 lock_wait_timeout 默认 1 年 → DROP 长期失败 → 真正枯竭
```

| 层 | 是什么 | 现有手段 | 状态 |
|---|---|---|---|
| ① 库残留 | 没人 DROP 的 scratch 库 | 两个回收器 | **判据分歧** |
| ② 连接残留 | 进程死但连接未断 | 进程退出自然回收 | 基本自愈 |
| ③ **MDL 残留** | DROP 被元数据锁挂住 | 仅 `lock_wait_timeout` fail-fast | **回收器治不了** |

**回收对象仅一类**：测试产生的 MySQL scratch 库（`bg_` 前缀族）。**不动**日志、构建产物、`var/` 文件、worktree 目录、git 对象；**永不回收** `broker_gateway`／`broker_gateway_dev`。

### 5.2 两个回收器的判据矛盾（实测）

| | `scripts/dba/mysql_test_db_gc.sh` | `scripts/tools/reap_stale_scratch.py` |
|---|---|---|
| 认领前缀 | `broker_gateway_t83_test_` ＋ `bg_scratch_` | **仅 `bg_`** |
| 可回收判据 | **`kill -0 <pid>` 失败** | **超龄 30 分钟 ＋ 无活动连接** |
| 默认模式 | **dry-run** | **直接执行** |

**后果**：
1. **对同一库可给出相反结论**——跑了 40 分钟但仍存活的库：Python 判"超龄＋无连接，该删"，bash 判"属主存活，跳过"。**"无活动连接" ≠ "没人要了"**（测试可能处在两次连接之间）。
2. **前缀漂移盲区**——R-D-41 已统一到 `bg_`，但 bash 侧仍留旧族；反之 Python 侧看不见旧族。**盲区比没有回收器更糟：它看起来像有人在管。**

### 5.3 租约层设计

**三套状态域，语义不可混用**：

| 状态域 | 语义 | 释放方式 | 崩溃后 |
|---|---|---|---|
| **任务所有权** | `owner` 谁在办 | **必须显式** | 留在原地等人处理 |
| **资源租约** | scratch 库配额、测试槽 | **可 TTL 自动回收** | TTL 到点自动归还 |
| **合并队列** | 串行 FIFO ＋ 硬闸 | **必须显式** | 队列可重建 |

> 任务所有权若用 TTL 释放，活就没人干了；资源租约若要显式释放，进程一崩就永久泄漏——**现系统正好是后者**。

**租约记录**：

```
lease_id · class(bg_db|test_slot|disk) · holder(worktree/pid/branch/条目号)
db_name · n · bytes · created_at · ttl · state(active|reclaimable|reclaim_tracking|reclaimed)
```

**活性判定**：**复用现有最稳的判据**——库名内嵌 pid → `kill -0 <pid>`。**不需要心跳。**
**pid 复用防护**：加 `/proc/<pid>/stat` 的 starttime 一起比对；或依赖 TTL 兜底。

**申请与回收**：

```
acquire_slot(class=bg_db)
  → 配额满？ → 即时回收 reclaimable（holder 已死／TTL 过期）
             → 仍满 → 排队（返回队位）
  → 发放 → 返回 lease_id ＋ db_name

reclaim(lease_id)
  → processlist 无引用？ → SET SESSION lock_wait_timeout=<秒级> → DROP → 留痕
```

**双路回收**：定时扫（兜底）＋ **申请入口即时回收**（关键，否则枯竭换个地方发生）。

### 5.4 归属裁定

回收器**混了两个不同性质的东西**，现状是**判定层被复制成两份**——**这才是分歧根因，不是"放错了目录"**：

| 层 | 内容 | 性质 | 归属 |
|---|---|---|---|
| **判定层** | 哪些库是 scratch、属主是谁、还活着吗、能删吗 | 资源属主与活性 | **协调器**（租约状态的副产品） |
| **执行层** | 执行 DROP、处理 MDL、实例级权限 | 实例运维动作 | **dba** |

拆开后，回收器**退化为纯执行器、不持有任何判据**，判据分歧从结构上消失。

**边界**：协调器**自己不做 DROP**——它不直接接触真实数据库。实际释放由 dba 回收器执行。

### 5.5 配额与标定

配额数（库上限／磁盘上限／触库并发）**现在不知道**，且**鸡生蛋**。

**处置**：**先设保守初始值并只观测不放行**（标定期），用真实负载标定后再启用配额闸。**不在设计阶段猜数。**

### 5.6 未解决：MDL 层（③）

租约层解决 ①库残留，**未碰 ③MDL 残留**——而 ③ 才是 R-D-41 亲历事故的直接原因。

**须单独立项**：治**持锁会话的来源**（建库方亦须设 `lock_wait_timeout`，异常时确保回滚关闭）。
**本方案不宣称已解决枯竭。**

## 6. 合并队列

### 6.1 触发

TL／commander **显式触发**。

### 6.2 六条硬闸

| # | 闸 | 治什么 |
|---|---|---|
| 1 | 条目状态 = delivered | 无实测即合并 |
| 2 | commit 改动文件 ⊆ 条目白名单 | 越范围合入 |
| 3 | **门禁实证存在且可核**（落盘路径可读） | 证伪"台账先于核验" |
| 4 | 基座已含 `main` 最新 | 过期基座合入 |
| 5 | 同一时刻**只有一次合并** | git 索引竞态 |
| 6 | **内容冲突即拒** → 转动作项给 TL | 语义问题 ≠ 时序问题 |

### 6.3 串行化能解决与不能解决

**能**：git 索引竞态。公约现有的「合并后必须复核 `git diff --stat` 是否为空、否则先 `merge --abort` 再重做」「共享检出上提交用 `git commit -- <显式路径>`」——这些补丁存在的唯一原因就是**没有串行化**，可全部删除。

**不能**：内容冲突。**冲突是语义问题，不是时序问题。** 协调器**永不自动解冲突**。

### 6.4 边界与风险

- 协调器**不跑 pytest**，只读 TL 独立重跑的实证。
- **推送仍归 commander**（不可逆动作，暂不收入）。
- 队列必须**可观测**（谁在队、队位、卡在哪个闸）。
- **`claim` 与 `request_merge` 必须解耦**——队列项不得持有任何任务所有权（防等待环）。
- **待合分支数须实测**（18 活跃／128 目录，不是 128 个待合）。

## 7. 监视机制

### 7.1 形态：脚本定时 ＋ LLM 事件驱动

| 监视器 | 扫什么（＝协调器 delta） | 唤醒谁 |
|---|---|---|
| OPS | OPS 条目新增／超时未闭环 | OPS 会话 |
| DBA | **有 revision 无评审记录**；降级保真未对表 | DBA 会话 |
| PO | 跨线积压越阈；同资源跨线争用 | PO 会话 |
| 线 PM ×6 | 本线新 R；**已交付未验收** | PO（转 PM） |
| TL ×6 | 本线**已定稿未认领** | TL 会话 |

**为什么必须是脚本**：
1. **不占 ⑧ 额度**（脚本非 LLM 子代理）；
2. **不违 ⑨ 禁空转**（"等待"发生在脚本里，LLM 只在 delta 非空时启动）；
3. **无 sleep／轮询**（轮询在 cron，不在子代理）。

### 7.2 三档去重闸

| 档 | 何时报 | 理由 |
|---|---|---|
| 明细 diff | 编号集合增／删／状态位变化 | 机械可判，误报≈0，**默认全报** |
| 首次发现 | 一条 `[未处理]` 第一次被看见 | 简报一次 |
| **超时** | 仍在原地超 N 小时／天 | **必须报**——把"漏看"变成"迟到" |

### 7.3 DBA 触发器勘正

DBA 的主触发**不是扫 inbox**，而是「**新增 alembic revision 但无 dba 评审记录**」——可机械判定，比"扫 inbox 猜哪条跟我有关"可靠。

| 同一 (状态,事件) 确定性 | ✅（`define` 歧义已修） |
| **`accept` 只可能来自 `verified`** | ✅ 结构上保证「形式有效是实质验收的前置」 |
| 返工闭环（`delivered`→`reverify`→`in_progress`→`deliver`） | ✅ 可循环，`round` 递增，无死锁 |
| 非法路径结构上不可达 | ✅（如"未定义即交付""未校验即验收"均不成立） |
| 阻塞不造成死锁 | ✅ 保留进入前状态 |
| 强制转换显式 | ✅ 仅 `override`，留痕 |

## 10. 非目标

1. **不做事件溯源的所有权转移**——markdown 仍是可读视图，不是历史归档的唯一载体。
2. **不自动解合并冲突**——协调器不"理解代码"。
3. **不追求消除 git 延迟**——worktree 仍需 `pull` 才能看到最新视图；但已从"合并义务"降为"拉取事项"。
4. **不替 OPS／DBA 执行特权动作**。
5. **不在设计阶段猜配额数**。

## 附：一句话总结

**角色链与状态机是稳的**：PO 派 PM、TL 派 dev、commander 做业务合并，三链无交叉；三个状态机均可判定、无死锁、无不可达。

**架构核心是一句话**：**"现在是什么"归协调器（仓库外的 append-only 事件），"曾经发生过什么"归 commit；markdown 从双向账本降为单向渲染（兼容视图 ＋ 人读报告）。**

**最大的单点收益是一句话**：**格式松绑不是少写竖线，而是让原本只能写在散文里的东西——白名单冲突、验收实证——终于可以被机器判定。**

**对"不要把文档丢过来"的回答**：协调器**自己跑审核、自己留证据链**，只递**异常与需要决定的事**。
> 14 项审计数字、61 份 SUBMISSION 路径、1054 行线板**不进报告**——它们该被协调器消化成异常，或被一次 `trace <id>` 查询取回。
> 但有一条边界不能越：**协调器只判"形式有效"，不判"内容正确"**——机械通过 ≠ 实质正确。
