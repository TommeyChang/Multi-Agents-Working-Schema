# bindings — 工程绑定

**体系管机制，工程管落点。** 本目录装的就是"落点"。

## 一、为什么要这一层

角色文件（`agents/`）与规则（`rules/`）只该写**换一个工程还成立**的东西：
角色形与属、权限、状态机、不变量、交接面。

而"本工程有哪几条线、各线工作面是哪些路径、门禁跑什么、受保护资产叫什么、部署窗口分几段"——
**换个工程就不成立**。把它们写进角色文件，就会变成**看起来像规则、实际是某一工程的巧合**：
读者分不出哪句是机制、哪句是那个工程的现状。**错得不像错的**，是这里最贵的失败形态
（本体系就是从那个状态走过来的：`agents/dev.md` 里曾写着 `auth/`、`broker_gateway/`、
`data_access/`，`agents/dba.md` 里写着 `bg_tmpl_*`）。

**判据一句话**：*"换一个工程，这句话还成立吗？"* 成立 ⇒ 体系侧；不成立 ⇒ 写进绑定。

## 二、放哪（解析顺序固定）

| 位置 | 什么时候用 |
|---|---|
| `<主干>/.maws/project.md` | **优先**。随工程版本走：可评审、可 diff、可回滚（设计上的正位） |
| `bindings/<工程目录名>.md` | 兜底。体系侧登记——**当前工程用的就是这条**（改动面限定在体系内、不动生产仓时） |

`coord bind` 与协调器都按这个顺序找。**将来把绑定搬进主干，机制一行不用改**：
`bg_coordinator/binding.py` 的 `candidates()` 已经按优先级排好。

## 二·五、绑定归哪个仓的 VCS（**不开独立仓**）

绑定**没有、也不该有自己的 VCS**——它必须寄居在某个仓里：

| 放哪 | 谁的历史里能看到它 | 什么时候用 |
|---|---|---|
| **工程仓** `<主干>/.maws/project.md` | 工程自己的 `git log`／diff／回滚／审批面（`git log -- .maws/` 可单独查） | **设计正位**：随工程版本走 |
| **体系仓** `bindings/<工程>.md` | 体系的历史 | 临时：改动面限定在体系内、不动生产仓时（当前工程就是这条） |

**为什么不开独立仓**：

1. 绑定的变更必须与它描述的东西**同批评审**——改了工作面却不改代码、改了门禁却不改流水线，
   那种变更**没人会看**；独立仓等于把它从工程评审里摘出去；
2. 它要落在**现有分权**里：线别与工作面是 **design 类（归 PO）**、受保护资产归 **DBA 面**、
   窗口段序归 **OPS 面**——独立 VCS 会把这三处的审批面拆散；
3. 三处并存必然漂移。本体系整套设计都在反「第二真相源」，这里不能自己开口子。

**两处并存会被报出来**：`coord bind` 检测未被采用的副本——**内容不一致**（真漂移）记缺口、
退出码 1；内容相同（冗余）也报出来但不阻断，因为**被忽略的那份不会停止变化**。
搬家的正确姿势是**删旧不留副本**，不是留一份"以防万一"。

## 三、格式

人读部分随便写；**机读部分是文件里第一个 ```json 块**。必需字段由
`bg_coordinator/schema.py::BINDING_FIELDS` 声明——**那是唯一权威**，
`binding.py` 只按它校验，不另立一份。

九个必需字段：

| 字段 | 装什么 |
|---|---|
| `project` | 工程名（与目标仓目录同名） |
| `version` | 绑定格式版本 |
| `lines` | 线别 → `{name, workface[]}`：本工程有哪几条线、各线工作面 |
| `gate` | 门禁：入口／快跑标记／域映射／共享面／静态腿／发布口径／真库并发纪律 |
| `migrations` | 迁移目录、工具、命名、已知坑 |
| `protected_assets` | 受保护资产（回收器永不触碰） |
| `scratch_namespace` | scratch 命名空间前缀 |
| `window` | 部署窗口段序 |
| `shared_files` | 共享面（改动须串行或单点改） |

**空值算缺口**。"有字段但空着"是最危险的形态——它看起来像已经声明了，所以校验器把
空字符串／空对象／空数组一律算缺口，而不是放行。

## 四、给一个新工程上绑（五步）

1. 克隆本体系（不用 fork）：`git clone <本仓>`；
2. 在**目标工程**里写一份绑定：`<主干>/.maws/project.md`（照
   `futures-broker-gateway.md` 的样子，机读块填齐九个字段）；
   —— 若暂时不能动那个工程，就先写 `bindings/<工程名>.md`；
3. `coord --repo <目标仓> bind` ⇒ 应当是「完整」；有缺口它会逐条列出；
4. `coord maws` ⇒ 对账应当一致（绑定坏掉会在这一步报出来）；
5. 之后 `agents/`、`rules/`、`coordinator/` **一个字都不用动**——这正是这一层存在的收益。

协调器不知道目标工程在哪？用 `--repo <路径>` 或环境变量 `$BG_TARGET_REPO` 指定
（见 `bg_coordinator/target.py`，默认值只有那一处定义）。

## 五、还没定的两件事

1. **要不要"未上绑即拒派单"**。现在：未上绑时 `coord bind` 报缺口（退出码 1），
   但**不硬拦**派单——未上绑的工程仍可用。硬拦更符合"决策缺口必须暴露"，
   代价是新工程必须先补齐绑定才能动；这是要人拍板的取舍。
2. **工程侧已有文档的机制重叠**。工程自己的 `AGENTS.md`（共通纪律）与 `WORKTREE.md`
   （合入/回收口径）与本体系 `rules/SUBAGENT.md`／`rules/WORKSPACE.md` **内容重叠**。
   按设计应以体系为唯一权威、工程侧只留工程口径——但那要改生产仓，**未获授权前不动**。
